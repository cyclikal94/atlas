# Release packaging

The `Release` workflow builds native Linux AMD64/ARM64 and macOS ARM64 archives,
smoke-tested Linux AMD64/ARM64 container images and a Helm chart. Manual dispatch
uploads Actions artefacts only, even when run against a tag.

Pushing a tag such as `v0.12.0` publishes after all packaging jobs pass. The tag's
`MAJOR.MINOR.PATCH` must equal `info.version` in `api/openapi.json`; see
[API types package](#api-types-package).

- A GitHub Release containing native archives, the Helm chart, the API types package,
  `SHA256SUMS` and `container-image.txt` recording the multi-architecture image manifest.
- `ghcr.io/cyclikal94/atlas:vX.Y.Z`, containing both Linux architectures. The
  architecture tags `vX.Y.Z-amd64` and `vX.Y.Z-arm64` are also available.
- `oci://ghcr.io/cyclikal94/atlas/charts/atlas`, with chart version `X.Y.Z` and
  defaults pointing at the matching container image. Existing database Secrets
  are still required.

Tags must use `vMAJOR.MINOR.PATCH`, optionally followed by a SemVer prerelease
suffix such as `-rc.1`. Prerelease tags create GitHub prereleases. Build metadata
(`+...`) is not accepted, and no mutable `latest` container tag is published.
Review the corresponding Checks run and release evidence before pushing a tag;
the packaging workflow does not replace the full CI matrix or release gates.

Publishing uses the repository's `GITHUB_TOKEN`, with `contents: write` and
`packages: write` limited to the publish job. Ensure GitHub Actions is permitted
to publish packages; after the first publication, check that both GHCR packages
are public if anonymous pulls are intended. Existing packages must grant this
repository Actions access. Registry uploads and GitHub Releases are not one atomic
operation: a failed publication can leave registry images or a chart available.
Inspect that state before retrying; do not move an already published version tag.

Archives preserve executable permissions using tar and include checksums, revision,
lockfile hash, recovery tooling and configuration documentation. Dynamic OS libraries
are listed in `runtime-libraries.txt`; they must be installed on the target machine.
Linux archives built on Ubuntu 24.04 require a compatible glibc/OpenSSL environment;
use the Debian-based container for its pinned userspace. macOS archives target the
runner's OS/architecture and require the OpenSSL library reported by `otool`.

Build locally with `cargo build --release --locked -p atlas-server`, install
`cargo-about` 0.9.2 with `--locked --features cli`, then run:

```sh
scripts/package-release.sh aarch64-apple-darwin /tmp/atlas-release
```

Use the actual native build target. Package only a clean revision for publication;
a local package made from an uncommitted tree is a test artefact. Helm can be packaged
with `helm package deploy/helm/atlas`; supply existing database Secrets at deployment.

## API types package

Each release also carries the TypeScript declarations for the OpenAPI contract, for the
separately distributed web client to pin. There is no package registry: the transport is a
GitHub Release asset.

- `atlas-api-types-X.Y.Z.tgz`, the npm package `@atlas/api-types` (npm flattens the scope in
  the file name), where `X.Y.Z` is the tag without its leading `v`, prerelease suffix included.
- `atlas-api-types-X.Y.Z.tgz.sha256`, in `sha256sum -c` format. The same checksum is in
  `SHA256SUMS` and the release notes.

The package holds exactly `LICENSE`, `index.d.ts` (generated by the `openapi-typescript`
version pinned in `scripts/api-types/package.json` and its lockfile), `openapi.json` (the
exact contract), `package.json` and `provenance.json`. It contains declarations only: no
runtime code, dependencies, scripts or entry points. The fetch client (`openapi-fetch`) belongs
to the web client. `openapi.json` is there for tooling and compatibility checks; it is over
500 KB, so keep it out of a client bundle. `provenance.json` records `backend_commit`,
`contract_sha256`, `api_version` (the contract's `info.version`), `generator` and
`generator_lock_sha256`; the web client reads these names, so they do not change.

**Version rule.** A release tag's `MAJOR.MINOR.PATCH` must equal `info.version`, so the package,
the release and the contract carry one version. A prerelease such as `v0.12.0-rc.1` shares the
contract of `v0.12.0`. The build refuses any other tag before anything is published, because a
published tag must not be moved: raise `info.version` in the contract, and merge it, before
tagging. The server reports the contract version as `api_version` on `/health`;
see [API version and compatibility](api.md#api-version-and-compatibility).

**Build modes.** Only a pushed tag builds a releasable version, through `generate.mjs --release`
(and is verified with `verify.mjs --release`, below), which also needs a clean tracked working tree
and the Node version in `scripts/api-types/.node-version`. Manual dispatch builds `0.0.0-dev` and pull requests build
`0.0.0-ci`; neither is published. A local build uses `0.0.0-<label>`, for example
`0.0.0-bootstrap.<short commit>`, and is an unshipped diagnostic package, not release evidence.

```sh
npm ci --ignore-scripts --prefix scripts/api-types
npm test --prefix scripts/api-types
node scripts/api-types/generate.mjs --version 0.0.0-bootstrap.$(git rev-parse --short=8 HEAD)
node scripts/api-types/verify.mjs target/api-types/atlas-api-types-0.0.0-bootstrap.*.tgz
```

Generation needs `git` and `npm` on a POSIX system. It refuses a contract that differs from
`HEAD`, generates twice and rejects any difference, then builds the package twice under
different umasks and directories and rejects any difference in the tarball. Nothing is written
unless every check passes.

**Output location.** `--output` defaults to `target/api-types` in the repository root. `npm run
--prefix scripts/api-types` runs the script from `scripts/api-types`, so a relative `--output`
resolves there, not at the root. Both workflows therefore set one absolute `API_TYPES_OUTPUT`
(`$GITHUB_WORKSPACE/target/api-types`) and use it to generate, to verify and to upload;
`scripts/test_release_workflow.py` runs those commands in a scratch checkout and fails unless the
upload path finds exactly the tarball and its sidecar.

**Verifying an asset.** A matching sidecar shows that the bytes are unchanged since they were
published; it does not connect them to the tagged source. For that, download both files, check out
the release tag of this repository and verify with the expected release version, which is the tag
without its leading `v`:

```sh
sha256sum -c atlas-api-types-X.Y.Z.tgz.sha256
git checkout vX.Y.Z
npm ci --ignore-scripts --prefix scripts/api-types
node scripts/api-types/verify.mjs atlas-api-types-X.Y.Z.tgz --release --version X.Y.Z
```

`verify.mjs` always checks the sidecar, the archive entries and their modes, the manifest and
provenance, that `index.d.ts` equals a fresh generator run on the packaged contract, and that a
strict consumer typechecks under both `bundler` and `node16` resolution with `keyof paths` and
`keyof operations` equal to every path and `operationId` in the contract. It uses the generator
the package names, so verify with the same tag's lockfile.

With `--release --version X.Y.Z` it also compares the package with the checkout, which must have
a clean tracked tree: the recorded `backend_commit` must be the checkout's `HEAD`, the packaged
`openapi.json` must equal `api/openapi.json` at that commit, `generator_lock_sha256` must be the
digest of `scripts/api-types/package-lock.json`, the package version must be `X.Y.Z` and its
`MAJOR.MINOR.PATCH` must equal the contract's `info.version` (the rule the build enforces). A
package with correct-looking declarations but a misattributed commit, lockfile or version is
refused. The Release workflow does this for a pushed tag. The result reports
`"source_verified": true`; a release version cannot be verified without `--release`.

Without `--release` a package is a diagnostic and must be versioned `0.0.0-<label>`.
Its contents and declarations are still checked, but its recorded commit and digests are only
read back, never compared with a checkout, so the result reports `"source_verified": false` and
the command says so on stderr. That is the mode for a local or pull-request build and for
inspecting a package built elsewhere; it is not provenance evidence.

**Reproducibility.** For a given commit and version, on the pinned Node, the tarball is
byte-identical whatever the umask, checkout path, temporary directory, time or user. Its
declarations and its uncompressed tar stream are also identical across Node and npm versions
(checked between Node 22 and 25), but gzip output depends on the Node build's zlib, so a
rebuild on another toolchain should compare the tar stream, not the tarball:

```sh
gunzip -c atlas-api-types-X.Y.Z.tgz | sha256sum   # equals tar_payload_sha256 from generate.mjs
```

The tarball SHA-256 on the release page is authoritative. Consumers pin the asset URL and that
SHA-256 in their own lockfile and change the pin deliberately.

**Design choices.** File modes are set explicitly and the double build runs under different
umasks, rather than trusting the runner's environment. Provenance is checked against a
checkout the verifier is run from, which needs no signing service or registry. The Node version is enforced rather than
hand-writing a gzip encoder, whose bytes would vary between compressors anyway. A tar-stream
hash is reported instead of publishing a second asset. The Dependabot group for the generator
and `typescript` is reviewed by regenerating and diffing `index.d.ts` against the previous
release, because a generator bump changes every consumer's view of the API. Signing and
registry publication are not implemented.

## Dependency notices

`about.toml` and `packaging/notices.hbs` generate notices from the locked server graph
for the build target. Dev-only dependencies are excluded; build dependencies are
included conservatively because some generate code embedded in the executable.
`cargo-about --fail` rejects unresolved licences. The generator can retrieve missing
upstream licence information, so builds need network access or a populated cache.
The template links exact crate source archives, including the unmodified MPL `ece`
source. Coverage checks retain the copyright text previously held in `third-party/`.
See [cargo-about configuration](https://embarkstudios.github.io/cargo-about/cli/generate/config.html)
for the generator's selection rules.

The image includes generated Rust dependency notices, Rust standard-library notices,
OpenSSL and CA-package copyright files, plus the Debian base's existing notices.
Native archives include Rust notices; dynamic system libraries remain OS packages.
`cargo deny` is an independent policy/advisory check and does not create distribution
notices. Review notice changes when updating dependencies; generation is not a substitute
for reviewing unusual upstream licensing or source-availability requirements.
